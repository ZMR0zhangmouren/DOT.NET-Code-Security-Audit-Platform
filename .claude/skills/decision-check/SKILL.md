# /decision-check

扫 `./需求文档.md` 的改动(或整篇),对照 §11 决策记录表(Q1–Q17)逐条核验,列出冲突与风险。

## 触发方式

- `/decision-check <改动说明>` —— 用户描述改动意图,先扫描全文
- `/decision-check --diff` —— 只对照 git diff(若根目录已 git init)
- `/decision-check --all` —— 强制全量扫描(忽略 diff)

## 工作流

1. **读取决策表**:从 `./需求文档.md` §11 抽取 Q1–Q17 的"(锁定决策)"列,得到 17 条铁律
2. **读取需求文档全文**(或仅 diff 块),抓出每条主张/数值/枚举/技术选型
3. **冲突检测**:对每条铁律,在文档其它位置搜索:
   - 反向陈述(如"不脱离 Copilot")
   - 不同数值(如"并发 4"vs"并发 2")
   - 缺失引用(如声称"按 Q7 锁定"但 §11 写的是不同策略)
   - 过时表述残留(LangGraph / "平台自建编排" / "Orchestrator 负责调度子 Skill")
4. **风险标记**:
   - 🔴 **冲突** —— 与决策表某条 Q 直接矛盾,必须修复
   - 🟠 **漂移** —— 文档某处倾向偏离决策,但未明说(需用户确认)
   - 🟡 **过期** —— 引用了旧版决策(如 Q8 MVP 漏洞状态流转 = 否,而 §5.5 实际改为部分流转)
5. **产出报告**:每条冲突给出"决策原文 / 文档原文 / 修复建议"三段式

## 关键决策清单(Q1–Q17 速查)

| # | 锁定决策(简) |
|---|---------------|
| Q1 | 后端 = NestJS(TS) |

| Q8 | MVP 漏洞状态流转 = 部分(库级进 MVP,实例级仍 Phase 2) |
| Q9 | 数据脱敏导出 = 不需要 |
| Q10 | 内置漏洞样本集 = 是,Phase 1 ≥ 30 样例 |
| Q11 | 部署 = 本地直跑 Node + SQLite,Docker Phase 4 |

## 注意事项

- 仅诊断,**不自动修改**;把修复建议交回用户拍板
- 若 §11 决策表本身被改动,**先警告用户**并要求先在 §11 追加/修改决策,再做全文检查
- 不覆盖 README/子仓库 README 的差异(那是真理之源,改动要慎重)
